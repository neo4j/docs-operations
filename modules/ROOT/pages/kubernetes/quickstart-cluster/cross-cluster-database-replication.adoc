[[cross-cluster-database-replication]]
= Cross-cluster database replication

Cross-cluster database replication (CCDR) keeps a read-only replica database in an independent Neo4j cluster.
The upstream and replica clusters must run compatible Neo4j versions.
Follow the xref:clustering/replicating-databases-across-clusters.adoc[Clustering -> Replicating databases across clusters] for the release-specific compatibility rules, Cypher syntax, disaster recovery recommendations, and other aspects of managing CCDR.

For details on code and file examples, refer to the link:https://github.com/neo4j/helm-charts/tree/dev/examples/ccdr[Neo4j Helm chart repository]. 


[[network-replication]]
== Configure replicating databases across clusters via network

Install every member of each Neo4j cluster as a separate Helm release.
Start with the common values in _source-cluster-values.yaml_ and _replica-cluster-values.yaml_.

.source-cluster-values.yaml
[source,yaml]
----
neo4j:
  name: ccdr-source
  edition: enterprise
  acceptLicenseAgreement: eval
  minimumClusterSize: 3

volumes:
  data:
    mode: defaultStorageClass

services:
  neo4j:
    enabled: false
  ccdr:
    enabled: true
    annotations: {}
    spec:
      type: ClusterIP

ssl:
  cluster:
    privateKey:
      secretName: cluster-tls
    publicCertificate:
      secretName: cluster-tls
    trustedCerts:
      sources:
        - secret:
            name: source-cluster-ca
        - secret:
            name: replica-cluster-ca
----


.replica-cluster-values.yaml
[source,yaml]
----
neo4j:
  name: ccdr-replica
  edition: enterprise
  acceptLicenseAgreement: eval
  minimumClusterSize: 3

volumes:
  data:
    mode: defaultStorageClass

services:
  neo4j:
    enabled: false
  ccdr:
    enabled: true
    annotations: {}
    spec:
      type: ClusterIP

ssl:
  cluster:
    privateKey:
      secretName: cluster-tls
    publicCertificate:
      secretName: cluster-tls
    trustedCerts:
      sources:
        - secret:
            name: replica-cluster-ca
        - secret:
            name: source-cluster-ca
----

Allow a new cluster to become healthy using the chart's default internal addresses.
Then perform a rolling update, assigning a unique externally reachable address to each member while ensuring cluster health is maintained:

[source,yaml]
----
config:
  server.cluster.advertised_address: source-1.example.com:6000

services:
  ccdr:
    enabled: true
    annotations:
      # Add provider-specific annotations for an internal load balancer here.
    spec:
      type: LoadBalancer
----

`services.ccdr` creates a service selecting only that Helm release's pod and exposes only `TCP 6000`.
Enable it only for members that must accept CCDR traffic.
Prefer private addresses and restrict ingress to the replica cluster's network.
If both clusters share routable Kubernetes DNS and networking, `ClusterIP` is sufficient.

For GKE clusters in different regions, _gke-network-values.yaml_ creates private internal load balancers with global access enabled so clients in other regions of the same VPC, or connected VPC networks, can reach them.

.gke-network-values.yaml
[source,yaml]
----
services:
  ccdr:
    annotations:
      networking.gke.io/load-balancer-type: Internal
      networking.gke.io/internal-load-balancer-allow-global-access: "true"
    spec:
      type: LoadBalancer
      externalTrafficPolicy: Cluster
----

. Configure advertised addresses.
+
The advertised address is not inferred from a `LoadBalancer` because the address may be allocated asynchronously.
Explicitly configure xref:configuration/configuration-settings.adoc#config_server.cluster.advertised_address[`server.cluster.advertised_address`] with the stable DNS name or IP assigned to that member's CCDR service.
+
Update advertised addresses one member at a time.
Do not update all members simultaneously, and do not use the external addresses during the initial `system` database bootstrap.
Follow the steps for each cluster member:
+
* Wait for the cluster to become healthy.
* Update the advertised address of a cluster member at a time.
* Wait for that cluster member to become ready again.
* Repeat the process for the next member.

. Configure inter-cluster TLS.
+
For encrypted inter-cluster traffic, configure `ssl.cluster` in both clusters.
Each cluster must trust both its own CA and the remote cluster's CA.
Ensure that the certificate SANs include the advertised address of each cluster member.
The Helm values files specify the expected secret mounts.
Create all referenced Kubernetes secrets before installing the Helm releases.

. Create the source and replica databases.
+
After all members are reachable, create the source database and the replica database using the syntax documented for your Neo4j version.
Supply the three upstream `host:6000` endpoints in xref:clustering/replicating-databases-across-clusters.adoc#syntax-create-replica-db-via-network[`replicaConfig.addresses`].
For syntax and detailed instructions, see xref:clustering/replicating-databases-across-clusters.adoc#create-replica-via-the-network[Creating a replica database via the network].


[[backup-pull-replication]]
== Configure replicating databases across clusters via backup pulling

Backup-pull based CCDR does not require `services.ccdr`.
You have to configure a `neo4j-admin` backup job to continuously extend and upload an unbroken backup chain.
Then create a replica with a xref:clustering/replicating-databases-across-clusters.adoc#create-replica-db-via-backups[`replicaConfig.pullURI`] pointing at that object-storage location.
Files _backup-pull-job-gcp-values.yaml_ and _backup-pull-replica-values.yaml_ provide GKE-oriented starting points.

.backup-pull-job-gcp-values.yaml
[source,yaml]
----
neo4j:
  # Use the backup image version matching the Neo4j DBMS version.
  imageTag: {neo4j-helm-chart-version}
  jobSchedule: "*/5 * * * *"

backup:
  databaseBackupEndpoints: "source-1-admin.source.svc.cluster.local:6362,source-2-admin.source.svc.cluster.local:6362,source-3-admin.source.svc.cluster.local:6362"
  database: ccdr-source
  cloudProvider: gcp
  # Replace with a GCS bucket and prefix available to the service account below.
  bucketName: replace-me/ccdr-source
  preferDiffAsParent: true
  remoteAddressResolution: true
  keepBackupFiles: false

# Bind this Kubernetes service account to a Google service account with write access to the bucket.
serviceAccountName: neo4j-backup
----

.backup-pull-replica-values.yaml
[source,yaml]
----
neo4j:
  name: ccdr-replica
  edition: enterprise
  acceptLicenseAgreement: eval
  minimumClusterSize: 3

volumes:
  data:
    mode: defaultStorageClass

services:
  neo4j:
    enabled: false
  ccdr:
    enabled: false

podSpec:
  # Bind this Kubernetes service account to a Google service account with read access to the backup bucket.
  serviceAccountName: neo4j-backup-reader

config:
  # The backup-pull RPO includes both the backup job cadence and this polling interval.
  db.cluster.backup.pull_interval: 1m
----

When `backup.remoteAddressResolution` is enabled, every source member must advertise a backup address that the backup job can resolve.
Set this per Helm release, for example: `server.backup.advertised_address=source-1-admin.source.svc.cluster.local:6362`.
Leaving the default `localhost:6362` causes the discovery service to succeed but the subsequent backup connection to fail.

The recovery point objective is the time between uploaded differential backups plus the replica pull interval.
The xref:configuration/configuration-settings.adoc#config_db.cluster.backup.pull_interval[`db.cluster.backup.pull_interval`] controls polling (defaults to `1m` in Neo4j 2026.06 and later).
For details, see xref:clustering/replicating-databases-across-clusters.adoc#_recovery_point_objective_rpo_2[Recovery point objective].
Broken or delayed backup chains increase the possible data-loss window, so monitor both the backup job and replica transaction lag.
